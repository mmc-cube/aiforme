## 第一部分：理解上下文工程

### 背景与动机

真实场景通常是这样的：开发者即兴开发了一个 MVP；之后因为上下文长度受限，只能开新 session 接着做。新 session 里，模型对之前的决策、边界、坑点一无所知，开发者只能一点点把"做过什么、为什么这么做、这次要改什么"重新输入。重复沟通、反复铺垫，效率直线下降。

后来开发者发现：把上次的重要内容"总结/压缩"进文档，下次开发时直接 @ 引用，就能把上下文串起来。这个朴素做法，后来被称为"上下文工程"。之后很多方法（SPEC、PRD、BMAD、工作流、角色分工）都是在它之上演进的外衣。

该方法追求的目标只有一个：让交付"质量可控"，过程"人工干预极少"，最好能"无人化"。

### SPEC、PRD、BMAD：外衣不同，本质相同

- **SPEC** 把需求拆成 requirements/design/tasks，看起来很专业，但经常把上下文碾得过碎，线性长闭环导致问题在集成/验收才爆。更糟的是，在一段时间里模型"降智"，就很难产出质量可控的代码。

- **PRD** 回到"做事用"的文档：目标、范围、验收口径清楚，能直接驱动实现与测试；不追求厚度，追求可执行。

- **BMAD** 引入角色做分工：PO 写 PRD、Architect 写 system architecture、SM 写 sprint plan，Dev/QA 执行与门控。实质仍是上下文工程：把关键口径写入对应产物，串好接力。

观察到很多团队花大量时间研究角色与工作流，结果是在换着方式做同一件事。思想不变：只用 PRD 也能产出可控的代码。更值得投入的是：如何保证整条交付链路质量可控，从需求到开发到测试到验收到上线的"少人干预，尽量无人化"。

### 什么是"上下文工程"（Context Engineering）

**定义**：围绕一次开发/调用时需要的上下文，做获取、筛选、组织、压缩与治理的系统化方法，让输出可控、可复现。

**为什么重要**：模型能力接近时，上下文更准、更干净、布局更好的系统，效果就更稳定（更低幻觉、更高成功率、更低时延与成本）。

#### 关键组成：

- **需求与评测**：任务定义、成功指标、离线/在线评测集合
- **上下文素材**：系统约束、用户意图、few-shot、工具 schema/结果、知识片段、会话状态
- **检索与重排**：BM25/向量/混合索引，查询改写，多跳检索，重排器
- **组织与布局**：信息分区与顺序（约束→工具→证据→示例→任务）、结构化格式、引用标注
- **压缩与预算**：摘要、去重、语义压缩、token 预算策略
- **路由与编排**：模型/提示选择，Agent/工具调用，回退与重试
- **安全与合规**：过滤、输出约束、工具白名单
- **观测与版本**：日志回放、A/B、数据血缘、模板/索引版本

#### 和 Prompt 工程的区别：

Prompt 工程偏"写好指令与示例"；上下文工程覆盖"检索、布局、压缩、路由、评测与治理"的全链路，是更大的系统工程。

#### 常见范式：

- **RAG 2.0**：查询改写 → 多索引检索 → 重排 → 证据去冗压缩 → 生成（带引用）
- **工具增强**：函数调用/工具执行 → 结果注入上下文 → 继续推理
- **记忆体系**：短期会话缓存 + 长期任务档案（可检索）
- **模板分层**：系统指令模块化 + 任务槽位化 + 证据段落

#### 关键指标：
任务成功率、可溯源性、幻觉率、引用命中率。

### PRD 一条路，也能跑出可控交付

PRD 要"轻但能用"，信息以可执行为准：

- Goals、FR/NFR、Epic、Stories、AC、Out of Scope（删赘述）
- 最少集：
  - 文件路径/函数签名
  - API 请求/响应与错误码
  - 数据迁移与回滚脚本
  - 配置项与灰度开关
  - 日志字段、监控指标与报警阈值

**关键门槛**：
1. 需求确认明确且获批准才开工
2. 规格必须"可执行"且完整

**流水线**：确认 → 规格 → 实现 → 评审 → 测试 → 验收。评审关注：需求符合、集成可行、代码质量、测试覆盖。

### 角色是分工，不是目的

- **PO** → 产出 PRD：目标/范围/AC 清楚，Out of Scope 明确
- **Architect** → 产出 system architecture：运行时、依赖、集成边界、迁移/回滚、观测前置
- **SM** → 产出 sprint plan：按"可见产物"的垂直切片排顺序
- **Dev/QA** → 执行与门控：变更清单、测试记录、质量门槛达标再过

复杂项目、多人协作时再引角色/并行流水线，用"各自的小上下文"减少污染与负担；别为了热闹而热闹。

## 第二部分：Claude Code约束系统实践

### Claude Code 项目驯化：从 Cursor 迁移的高效工作流

Claude Code 不仅仅是一个代码生成工具，更是一个智能的开发伙伴。然而，未经驯化的 Claude Code 就像一个有才华但没有规范的员工，可能会产生风格不一致、偏离项目需求的问题。

经过驯化和未驯化的 Claude Code，在代码可用性、调试能力、约束遵守方面几乎是两个工具。这套驯化体系能让 Claude Code 变得无比听话！

#### 核心理念：从被动使用到主动驯化

**传统方式的问题**：
- 每次都需要重新输入约束条件
- AI 容易"放飞自我"，代码风格不一致
- 缺乏项目整体概念和最终目标意识
- 容易遗忘之前的上下文和约定

**驯化系统的解决方案**：
1. **强约束框架** - 通过 `CLAUDE.md` 建立不可违反的规则
2. **文档联动机制** - 通过 `docs/` 文件夹实现知识传承
3. **状态驱动启发** - 通过 `status.md` 实现上下文记忆
4. **标准化工作流** - 通过 `workflow.md` 规范协作流程

### 驯化系统架构设计

#### 文件结构规划

```
project-root/
├── CLAUDE.md              # 项目宪法文件（强约束）
├── docs/                  # 政策库（规范性文件）
│   ├── brief.md          # 项目定位和功能描述
│   ├── schema.md         # 数据结构定义
│   ├── workflow.md       # 规范协作流程
│   ├── status.md         # 项目进度跟踪
│   └── kickoff.md        # 开工动员和权重分配
└── .claude/
    └── commands/         # 自定义命令
```

#### 约束层级设计

```
CLAUDE.md (强制约束) → docs/ (指导文档) → status.md (状态联动)
     ↓                    ↓                   ↓
  不可违反             指导性              动态状态
  项目标准             规范文件             进度跟踪
```

- 更新项目状态

#### 约束的渐进式强化

随着项目进展，逐步完善约束体系：
- 项目初期：基础技术栈约束和简单规范
- 项目中期：添加性能约束和完善安全规范  
- 项目后期：优化重构规范和文档维护要求

#### 多项目约束管理

对于多项目环境，建立约束继承机制。

多项目约束分层：
- 全局约束：通用编码规范和安全要求
- 项目特定约束：技术栈规范和业务规则  
- 临时约束：当前迭代重点和特殊需求

### 最佳实践和注意事项

#### 约束设计原则

**1. 明确性原则**
- 使用具体、可衡量的约束
- 避免模糊的描述
- 提供明确的判断标准

**2. 必要性原则**
- 只添加真正必要的约束
- 避免过度约束影响灵活性
- 定期清理过时约束

**3. 一致性原则**
- 确保约束之间不冲突
- 与团队规范保持一致
- 遵循行业最佳实践

**4. 可执行性原则**
- 约束应该可以被验证
- 提供检查和执行机制
- 包含违规的处理方式

#### 常见错误和解决方案

**错误 1: 约束过于严格**
- 问题：过度限制 AI 的创造力
- 解决：区分强约束和指导性约束
- 建议：将一些规范移到 docs/ 文件夹

**错误 2: 约束过于模糊**
- 问题：AI 无法准确理解和执行
- 解决：使用具体、可衡量的描述
- 建议：提供示例和判断标准

**错误 3: 忽视状态更新**
- 问题：AI 无法了解项目进展
- 解决：养成及时更新 status.md 的习惯
- 建议：在重要节点后主动更新状态

**错误 4: 文档维护不及时**
- 问题：约束和实际项目不同步
- 解决：定期审查和更新文档
- 建议：建立文档维护流程

## 第三部分：BMAD：上下文工程的完整实践案例

### BMAD框架介绍

BMAD-METHOD（Breakthrough Method of Agile AI-Driven Development）是上下文工程理论的完整实践实现。它通过专门的AI代理来模拟完整的敏捷开发团队，让一个人就能拥有整个团队的力量。

#### BMAD的核心思路

BMAD将上下文工程的关键组成部分具体化为一套完整的AI代理系统：

| 上下文工程概念 | BMAD实现 | 作用 |
|--------------|-----------|------|
| 路由与编排 | 角色命令系统 | /analyst, /pm, /architect, /sm, /dev |
| 组织与布局 | 智能模板系统 | 每个角色有标准化的输出模板 |
| 知识片段 | 文档联动机制 | 各角色生成的文档相互引用 |
| 会话状态 | 项目进度跟踪 | 完整的开发状态管理 |
| 系统约束 | 项目框架约束 | 自动化的项目约束管理 |

#### BMAD的功能优势

**1. 完整的敏捷团队模拟**
- 业务分析师（Analyst）：市场调研、需求收集
- 产品经理（PM）：PRD创建、功能优先级排序
- 架构师（Architect）：系统设计、技术架构
- 开发人员（Developer）：顺序任务执行、测试
- QA专家（QA）：代码审查、重构
- UX专家（UX）：UI/UX设计
- 产品负责人（PO）：需求管理
- Scrum Master（SM）：冲刺规划、故事创建

**2. 严格的敏捷工作流**
- 不是简单的AI助手，而是严格遵循敏捷方法论的完整流程
- 每个AI代理都有明确的职责和交付物
- 完整的需求→设计→开发→测试→交付流程

**3. 智能上下文管理**
- 一键切换角色，上下文自动保持
- 每个角色都能完整理解项目背景
- 专业输出：每个角色都按照标准模板输出专业文档

### BMAD的完整工作流程

BMAD采用6步敏捷开发流程：

1. **需求分析** (`/analyst`) - 项目背景调研和需求收集
2. **产品规划** (`/pm`) - PRD文档和功能优先级确定
3. **架构设计** (`/architect`) - 技术架构和API设计
4. **用户故事** (`/sm`) - 用户故事和验收标准定义
5. **开发实施** (`/dev`) - 代码实现和测试
6. **质量保证** (`/qa`) - 测试执行和质量验证
每个角色都有标准化的输出和职责，确保项目开发的专业性和一致性。

### BMAD的技术特性

**智能模板系统**
- 交互式文档模板和动态依赖加载
- 适用于任何项目类型

**灵活的开发模式**
- 渐进式开发（质量优先）和YOLO模式（快速原型）
- 根据项目需求灵活选择

**专业化AI代理**
- 角色专精和智能交接机制
- 模拟真实团队的协作方式

- 智能交接和自动进度跟踪
- 最小化人工干预

**可扩展的框架**
- 支持不同类型的项目和灵活配置

## 第四部分：实际应用详解

### 理论与实践的对应关系

上下文工程理论和约束系统实践本质上是同一个理念的不同表达。通过具体的实例可以更好地理解它们的应用。

#### 核心概念的对应关系

| 上下文工程概念 | 约束系统实现 | BMAD实践 | 作用 |
|--------------|-------------|----------|------|
| 系统约束 | CLAUDE.md | 项目框架约束 | 定义不可违反的规则 |
| 知识片段 | docs/ 文件夹 | 各角色文档 | 存储项目相关信息 |
| 会话状态 | docs/status.md | 进度跟踪 | 跟踪当前进度 |
| few-shot示例 | docs/ 中的代码示例 | 模板系统 | 提供参考模式 |
| 组织与布局 | 文件结构设计 | 智能模板 | 信息分区和顺序 |
| 路由与编排 | docs/workflow.md | 角色命令 | 协作流程规范 |

#### 解决问题的本质相同

**三者都解决同一个问题**：
```
AI对话无状态 → 需要重新解释 → 效率低下 → 代码不一致
```

**三者的解决方案**：
```
文档化约束 → 自动读取上下文 → 保持一致性 → 提高效率
```

### 开发实例对比

#### 三种开发方式的对比

**传统开发**：每次重新解释，代码风格不一致，效率低下
**约束系统**：自动读取约束，代码统一，效率显著提升
**BMAD框架**：完整敏捷流程，专业化分工，质量可控

#### 核心区别

- **上下文管理**：传统方式需要重复解释，约束系统自动读取
- **代码一致性**：传统方式风格混乱，约束系统保持统一
- **开发效率**：传统沟通成本高，约束系统专注功能实现
- **质量可控**：传统难以保证，约束系统自动遵循标准

### 文件组织结构

**约束系统文件结构**：
```
project/
├── CLAUDE.md              # 项目约束（自动读取）
├── docs/                  # 文档库
│   ├── brief.md          # 项目简报
│   ├── status.md         # 进度跟踪
│   └── workflow.md       # 协作流程
```
